# 短剧合并工具 · drama-merger

> 📚 **想深入理解实现？** 这里有一套 [13 篇循序渐进的实现教程](./docs/tutorial/README.md)，
> 从快速上手到源码解析（策略引擎、字幕重映射、合并即压缩、发布流水线、打包、踩坑集锦）。

把指定目录下的多集短剧，合并成一部完整的视频。

针对短剧场景做了三件事：**智能选策略**（能无损就不重编码）、**字幕时间轴自动重映射**（分集字幕各自从 0 开始，合并后会错位）、**音轨缺失自动补齐**。

---

## 快速开始

### 方式一：免安装版（无需 Python）

双击 **`打包.bat`**，约 1 分钟后生成 `dist/短剧合并工具/`。这个文件夹是**自包含**的：

```
dist/短剧合并工具/
    短剧合并工具.exe            ← 双击启动图形界面
    短剧合并工具-命令行.exe      ← 拖目录或命令行使用
    _internal/                  ← 运行时 + 捆绑的 ffmpeg（无需另装）
```

整个文件夹可直接拷到其他电脑（含未装 Python、未装 ffmpeg 的机器）使用。
两个 exe 共享同一份 `_internal`，ffmpeg 只存一份。

> 打包依赖 PyInstaller，`打包.bat` 会自动检测并安装（走清华镜像）。

### 方式二：源码运行（需 Python 3.11）

### 图形界面（推荐）

图形界面分两个标签页，对应两条前后相继的流水线：

```
① 合并视频     选目录 → 扫描分析 → 设选项 → 开始合并
② 发布准备     选成片 → 填剧名/封面 → 生成发布素材
```

「② 发布准备」会依据成片与素材生成三样东西：

| 产物 | 说明 |
|---|---|
| 章节时间轴 | 按各集真实时长累加，粘进简介后观众可直接跳集 |
| 发布文案 | YouTube 标题 / 简介（含章节）/ 中英标签，逐块可复制 |
| 缩略图 | 竖屏封面转 1280×720 横屏，自动去掉封面自带文字与水印 |

剧名匹配到内置模板时用现成文案；匹配不到则生成通用文案（可自行编辑）。
新增剧目的文案加在 `drama_merger/gui.py` 的 `DRAMA_TEMPLATES` 里即可。

双击 `启动界面.bat`，然后：选目录 → 扫描并分析 → 开始合并。

> 启动器会**优先使用打包版**（若存在），否则回退到系统 Python。

### 命令行

```bash
# 1. 先看看目录里有什么，能不能无损拼接（不改动任何文件）
python cli.py probe "D:/短剧/某剧"

# 2. 合并
python cli.py merge "D:/短剧/某剧" -o "D:/输出/某剧全集.mp4"

# 3. 合并即压缩（一次成型，不产生中间大文件）
python cli.py merge "D:/短剧/某剧" --compress

# 4. 由成片生成发布素材（章节 / 文案 / 缩略图）
python cli.py publish --source "D:/短剧/某剧" -o "D:/输出/youtube"

# 5. 查看压缩档位
python cli.py presets
```

或者直接把短剧目录**拖到 `合并.bat` 上**，一步完成探测 + 合并 + 字幕。

### Windows 批处理注意事项

`.bat` 文件必须满足两个条件，否则会报 `'xx' 不是内部或外部命令`：

1. **换行符必须是 CRLF**（`0d 0a`）。用 Git/Linux 工具生成时容易变成纯 LF（`0a`），
   CMD 会把两行拼成一条命令执行，出现乱码报错。
2. **编码用 GBK（ANSI 936）**，与中文 Windows 控制台原生一致，无需切代码页。

仓库内的 `.bat` 均已按此处理。如需新增或改动，用 Python 写字节而非文本编辑器保存：

```python
from pathlib import Path
text = "...".replace("\n", "\r\n")          # 强制 CRLF
Path("xxx.bat").write_bytes(text.encode("gbk"))
```

## 合并策略

工具会先探测每个片段的参数，再自动选最省的方案：

| 策略 | 触发条件 | 速度 | 画质 | 实测（本机 1080×1920） |
|---|---|---|---|---|
| **A 无损拼接** | 所有片段参数完全一致，且不裁剪/不淡变 | 极快 | **零损失** | 18s 素材 **0.3 秒**完成（60x 实时） |
| **D 最小重编码** | 多数片段一致、少数偏离 | 快 | 仅偏离片段损失 | 36 集里 1 集偏离，只编码那 1 集 |
| **E 合并即压缩** | 指定了 `--compress` 且参数一致 | 中 | 一次损失 | 7min 素材 **195 秒**（2.1x 实时） |
| **B 归一化拼接** | 参数有差异（分辨率/帧率/音轨等） | 快 | 一次损失 | 15s 素材 **3.1 秒**（4.8x 实时） |
| **C 滤镜重编码** | 策略 E/B/D 失败时的兜底 | 较慢 | 一次损失 | 15s 素材 2.1 秒（7.3x 实时） |

**关键点：策略 A 不重新编码**，只是把原始码流按顺序拼接，所以是"秒级完成 + 画质零损失"。短剧素材通常同源同参数，命中率很高。

策略 B 会先各片段统一到同一参数（取多数派分辨率 + 最高帧率），再无损拼接——所以只损失一次画质。

策略 E 是策略 A 的"压缩版"：同样按顺序拼接，但边拼边编码，一次成型。

## 常用参数

```
-o, --output        输出文件路径（默认 <父目录>/<目录名>_merged.mp4）
-r, --recursive     递归搜索子目录
-n, --limit         只合并前 N 个片段（快速验证用）
--strategy a|b|c    强制指定策略
--compress [档位]   合并即压缩（一次成型）。不带值默认 upload 档
--encoder auto|nvenc|x264   编码器（auto = 自动择优）
--crf 20            画质，越小越清晰（默认 20）
--trim-head 2       裁掉每集开头 2 秒（去片头）
--trim-tail 3       裁掉每集结尾 3 秒（去片尾）
--fade-in 1         整片开头淡入 1 秒
--fade-out 1        整片结尾淡出 1 秒
--subtitles         生成外挂字幕
--burn-subtitles    烧入硬字幕
--dry-run           只打印命令，不执行
--keep-temp         保留临时文件（排错）
--verbose           显示详细环境信息
```

> `--compress` 会改变默认输出文件名（附加档位后缀，如 `xxx_H264-CRF26.mp4`），
> 避免与未压缩成片混淆。用 `-o` 显式指定路径时不受影响。
> `--compress` 与 `--trim-head`/`--fade-in` 可叠加使用。

**去片头片尾**是很实用的组合（短剧每集开头常有重复的前情提要）：

```bash
python cli.py merge "D:/短剧/某剧" -o out.mp4 --trim-head 3 --trim-tail 5 --subtitles
```

## 字幕处理

短剧的字幕有个隐蔽陷阱：**每一集的字幕都从 `00:00:00` 开始计时**。直接拼接会让第 2 集之后的字幕全部提前，第 2 集的对白会出现在第 1 集的时间段里。

工具会自动：

1. 为每集视频寻找配套字幕（同目录同名 → 同名前缀 → 目录内唯一字幕文件）
2. 按每集在成片中的起始位置**整体平移时间轴**
3. 合并输出整片字幕

实测效果（3 集 × 6 秒）：

```
第1集.srt (+0.00s,  3条)
第2集.srt (+6.00s,  3条)
第3集.srt (+12.00s, 3条)
```

支持 SRT / VTT / ASS 三种格式，输出沿用原格式。

## 合并即压缩（推荐）

**合并的同时直接压缩，一次成型，不产生中间大文件。**

过去要先合并出 2.7GB 的成片、再跑一次压缩，既占磁盘又多一次编解码。
现在给 `merge` 加 `--compress` 即可一步到位：

```bash
# 默认 upload 档（体积约减 70~80%）
python cli.py merge "D:/短剧/某剧" --compress

# 指定档位
python cli.py merge "D:/短剧/某剧" --compress hevc        # HEVC，体积再省一半
python cli.py merge "D:/短剧/某剧" --compress hevc-light   # 体积最小

# 查看所有档位
python cli.py presets
```

图形界面里也加了同款开关：勾选「合并时直接压缩」再选档位即可。

**实测**（36 集短剧，1080x1920@30fps）：

| 方式 | 素材 | 产出 | 中间文件 | 耗时 |
|---|---|---|---|---|
| 先合并再压缩 | 2.7 GB | 108 MB | **2.7 GB 中间文件** | 合 31s + 压 194s |
| **合并即压缩** | 2.7 GB | 108 MB | **无** | 约 195s |

画质与时长完全一致，省掉了中间文件的磁盘占用和一次封装开销。

> 实现上，参数一致的素材走 concat demuxer 直连编码（策略E）；
> 参数有差异时逐片段归一化并同时套用压缩参数（策略B），同样不产生中间大文件。

## 成片压缩（二次处理）

若你已有合并好的成片需要单独瘦身，用 `tools/compress_videos.py`。

```bash
# 只分析，看哪些值得压（不改动任何文件）
python tools/compress_videos.py --dir "成片目录" --analyze

# H.264 档位压缩（兼容性最好）
python tools/compress_videos.py --dir "成片目录" --preset upload

# HEVC 档位（体积再省一半，但老设备兼容性略差）
python tools/compress_videos.py --dir "成片目录" --preset hevc

# HEVC + 720p 上限（体积最小）
python tools/compress_videos.py --dir "成片目录" --preset hevc-light

# 校验通过后把原片移入回收站（可恢复）
python tools/compress_videos.py --dir "成片目录" --preset hevc --delete-original
```

### 档位对照

| 档位 | 编码 | CRF | 分辨率上限 | 相对原片体积 |
|---|---|---|---|---|
| `archive` | H.264 | 23 | 原样 | 约 40~60% |
| `upload` | H.264 | 26 | 原样 | 约 20~25% |
| `light` | H.264 | 28 | 720p | 约 15% |
| `hevc` | **HEVC** | 30 | 原样 | 约 8~10% |
| `hevc-light` | **HEVC** | 30 | 720p | 约 5% |

### 关键判断指标：bpp

不要只看 Mbps。**bpp（每像素每帧比特）= 码率 ÷ (宽×高×帧率)** 才是衡量码率是否虚高的正确指标：

- 短剧这类画面相对简单的竖屏内容，**bpp 0.08~0.15 已足够清晰**
- 超过 0.2 → 码率明显过剩，可压空间大
- 低于 0.06 → 已经压得很紧，同编码再压必然掉画质（但换 HEVC 仍可再省）

例：720p 跑 8 Mbps 看着不算离谱，但 bpp = 0.288，属于严重浪费；
反过来 1440×2560 跑 8.3 Mbps 的 bpp 只有 0.075，其实合理。

### 为什么用软编而非硬件加速

实测（1080p60 素材 60 秒样本，同为 CRF/CQ 26）：

| 方案 | 大小 | 速度 |
|---|---|---|
| x264 | 20.5 MB | 1.5x 实时 |
| NVENC | **45.5 MB** | 5.5x 实时 |

NVENC 快 3~4 倍，但**输出大一倍以上**——它追求吞吐量，编码效率本就弱于软编。
对"瘦身"这个目标，硬件编码是南辕北辙。故压缩场景默认走 libx264/libx265。

### 安全设计

压缩有损且耗时，脚本做了这些保护：

1. **原片不覆盖** —— 压缩版输出到独立目录
2. **自动识别不值得压的文件** —— 同编码且 bpp < 0.06 时跳过
3. **压缩后强制校验** —— 时长一致 + 分辨率未变大 + 抽样解码无错 + SSIM ≥ 0.95
4. **校验通过才处理原片** —— 且用**回收站**（可恢复），不是永久删除
5. **HEVC 兼容性配置** —— Main profile + yuv420p + hvc1 tag（老设备与 Apple 系都能播）

## 本机环境适配说明（重要）

本机同时装了两个 ffmpeg，**NVENC 支持情况完全相反**：

| ffmpeg | 版本 | NVENC 状态 |
|---|---|---|
| `imageio_ffmpeg` 自带 | 7.1 | **可用** ✅ |
| WinGet (Gyan full) | 8.1.2 | **不可用** ❌ |

ffmpeg 8.1.2 报错：

```
Driver does not support the required nvenc API version.
Required: 13.1  Found: 12.2
The minimum required Nvidia driver for nvenc is 610.00 or newer
```

当前驱动 560.94 < 610.00。而 ffmpeg 7.1 用的是较旧的 NVENC API（12.x），所以反而能用。

**因此工具不硬编码"能不能用硬件编码"，而是启动时实际跑一次编码测试**（`ffmpeg_env.py::_verify_nvenc`），再据此择优。这样将来升级驱动或换 ffmpeg 版本都不会踩坑。

本机实测（GTX 1080 Ti，16 核）NVENC 相对 libx264 veryfast 约 **2 倍**加速：

| 编码器 | 60 秒 1080×1920 素材耗时 |
|---|---|
| h264_nvenc (p4, cq 23) | 6 秒 |
| libx264 (veryfast, crf 23) | 13 秒 |

## 踩过的坑（都已在代码里解决）

**1. 时间戳 23 毫秒偏移**

最初用 `-avoid_negative_ts make_zero`，结果输出起始时间变成 `video=0.100s / audio=0.076s`，时长多出 23ms。

逐步排查发现：

- 纯 `concat + -c copy` → 视频起始 0.023s，时长 18.023s
- 加 `-copyts` → 起始 0.000000s，时长精确 18.000000s，帧数 432 恰好 = 18×24

单看 23ms 不起眼，但**逐集累积会造成长剧集音画漂移**，所以修掉了。最终方案是拼接阶段用 `-copyts`，并去掉 `-fflags +genpts` 和 `-avoid_negative_ts`。

**2. 无音轨片段拼接失败**

策略 C 最初用 `anull` 给无音轨片段补音轨，报错 `matches no streams`——`anull` 是音频滤镜，不能接视频流。

正确做法是**追加一路独立的 lavfi 静音输入，且必须指定时长**（不指定的话无限长的音源会让 concat 永不完结）。

**3. NVENC 的音画起点差**

NVENC 有约 3 帧编码器延迟。若在归一化阶段混用 `avoid_negative_ts`，会把延迟固化成 24ms 的音画起点差。归一化命令里刻意不加该参数，保证各片段起始时间干净归零。
