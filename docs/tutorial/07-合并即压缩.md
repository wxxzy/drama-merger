# 07 · 合并即压缩

> 对应源码：`drama_merger/compress.py` + merger.py 中的压缩相关逻辑
> 学习目标：理解压缩档位、bpp 判断指标，以及「为什么压缩必须用软编」。

## 问题：先合并再压缩太亏

过去的工作流是：先合并出 2.7GB 的大文件，再跑一次压缩得到 108MB。
缺点：

- 中间文件占 2.7GB 磁盘；
- 多一次封装/解封装开销；
- 视频被编码两次（合并一次 + 压缩一次）的隐患。

**合并即压缩**：给 `merge` 加 `--compress`，拼接的同时直接编码输出，一次成型。

| 方式 | 素材 | 产出 | 中间文件 | 耗时 |
|---|---|---|---|---|
| 先合并再压缩 | 2.7 GB | 108 MB | **2.7 GB** | 合 31s + 压 194s |
| **合并即压缩** | 2.7 GB | 108 MB | **无** | 约 195s |

## 压缩档位定义

`compress.py` 用一个 frozen dataclass 定义档位：

```python
# compress.py:24
@dataclass(frozen=True)
class CompressPreset:
    name: str            # 档位标识
    codec: str           # "x264" | "hevc"
    crf: int             # 画质（越小越清晰）
    audio_kbps: int
    max_height: int|None # 分辨率上限
    fps_cap: int|None    # 帧率上限
    speed: str           # 编码速度预设
```

五个内置档位：

| 档位 | 编码 | CRF | 分辨率上限 | 相对体积 |
|---|---|---|---|---|
| `archive` | H.264 | 23 | 原样 | 约 40~60% |
| `upload` | H.264 | 26 | 原样 | 约 20~25%（默认） |
| `light` | H.264 | 28 | 720p | 约 15% |
| `hevc` | HEVC | 30 | 原样 | 约 8~10% |
| `hevc-light` | HEVC | 30 | 720p | 约 5% |

`get_preset(name)` 按名取档位，`describe_all()` 生成 CLI 展示文本。

## 压缩如何融入合并

档位被注入 `MergeOptions.compress`，`merger.py` 据此走两条路：

- **参数一致 → 策略 E**：`build_encode_concat_cmd()` 用 concat demuxer 直连 + 一次编码，
  中间不落地任何大文件；
- **参数有差异 / 有裁剪淡变 → 策略 B**：归一化时直接套用压缩参数
  （`_compress_encoder_args`），逐片段已是压缩后体积，仍无中间大文件。

编码参数由 `_compress_encoder_args()` 生成：

```python
args = ["-c:v", preset.vcodec_name, "-preset", preset.speed,
        "-crf", str(preset.crf), "-pix_fmt", "yuv420p"]
if preset.codec == "hevc":
    args += ["-profile:v", "main", "-tag:v", "hvc1", ...]  # 兼容性
```

HEVC 特意用 Main profile（非 Main10）+ `hvc1` 标签：老设备能播，Apple/QuickTime 也能识别。

## 关键判断指标：bpp

不要只看 Mbps，**bpp（每像素每帧比特）= 码率 ÷ (宽×高×帧率)** 才是判断码率是否虚高的正确指标：

- 短剧这类简单画面的竖屏内容，`bpp 0.08~0.15` 已足够清晰；
- `> 0.2` → 码率明显过剩，可压空间大；
- `< 0.06` → 已压得很紧，同编码再压必然掉画质（但换 HEVC 仍可再省）。

例：720p 跑 8 Mbps 看着不算离谱，但 bpp = 0.288，属于严重浪费；
反过来 1440×2560 跑 8.3 Mbps 的 bpp 只有 0.075，其实合理。

`tools/compress_videos.py` 的 `--analyze` 模式就用 bpp 判断哪些文件值得压，
同编码且 bpp < 0.06 的直接跳过。

## 为什么用软编而非硬件加速

实测（1080p60 素材 60 秒样本，同为 CRF/CQ 26）：

| 方案 | 大小 | 速度 |
|---|---|---|
| x264 | 20.5 MB | 1.5x 实时 |
| NVENC | **45.5 MB** | 5.5x 实时 |

NVENC 快 3~4 倍，但**输出大一倍以上**——它追求吞吐量，编码效率本就弱于软编。
对「瘦身」这个目标，硬件编码是南辕北辙。故压缩场景一律用 `libx264`/`libx265`。

## 成片压缩（二次处理工具）

如果已有成片要单独瘦身，用 `tools/compress_videos.py`（独立于合并流程）：

```bash
python tools/compress_videos.py --dir "成片目录" --analyze          # 只分析
python tools/compress_videos.py --dir "成片目录" --preset upload    # 压缩
python tools/compress_videos.py --dir "成片目录" --preset hevc --delete-original
```

安全设计：原片不覆盖 → 压缩后强制校验（时长一致 + 分辨率未变大 + 抽样解码 + SSIM ≥ 0.95）→
校验通过才把原片移入**回收站**（可恢复），不是永久删除。

## 小结

- 合并即压缩：策略 E（参数一致）或策略 B（有差异/裁剪），一次成型无中间大文件；
- 五档预设，H.264 兼容性好、HEVC 体积小；
- bpp 是判断码率虚实的核心指标；
- 压缩场景用软编，因为 NVENC 体积大一倍。
